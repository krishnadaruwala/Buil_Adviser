BuildAdvisor — 40% Progress Presentation

Hinglish speaking scripts · Frontend / Backend / Database · AI-Powered PC Build Recommender for Gamers

Shared Intro (koi bhi start kar sakta hai · ~30 sec)

"Good morning everyone. Hamara project hai BuildAdvisor — ek AI-powered PC build recommender for gamers. Idea simple hai: user apna budget aur target game daalta hai, aur hum usse ek complete, compatible aur priced PC build recommend karte hain, saath mein plain language explanation ki yeh build kyun sahi hai. Hamara tech stack bilkul SRS ke according hai — Streamlit frontend, Flask backend, SQLite database, plus Gemini API explanation ke liye aur live pricing. Aaj hum apne 40% milestone par hain, aur hum teeno apni-apni layer explain karenge."

🎤 Member 1 — Frontend Developer (Streamlit)

Screen par khula rakho: app.py, api.py

"Main ne frontend sambhala hai, jo hamare SRS ke according Streamlit mein bana hai — yeh ek Python framework hai jisse hum poori UI bina alag HTML, CSS ya JavaScript likhe bana sakte hain.

Hamara frontend ek thin client hai. Iska matlab — ismein khud koi business logic nahi hai. Har action HTTP ke through hamare Flask backend ko jaata hai, ek chhote client module api.py ke through. Isse hamari layers clean aur alag rehti hain, jo SRS Section 5.5 mein bola gaya hai.

Maine SRS Section 6.1 ke chaar screens banaye hain:

  1. Build Advisor — main screen. User ek slider se budget set karta hai, target game aur resolution/FPS choose karta hai, aur Generate Build dabata hai. Uske baad hum recommended parts, price table, estimated FPS, aur build kyun choose hui — yeh explanation dikhate hain. User build ko naam de kar save aur share link bhi kar sakta hai.
  2. Upgrade Advisor — un logon ke liye jinke paas already PC hai. Woh apna current CPU, GPU, RAM aur extra budget daalte hain, aur hum unka sabse bada bottleneck aur best single upgrade dikhate hain.
  3. Community — saved builds list karta hai aur users unhe rate kar sakte hain.
  4. Admin — password-protected dashboard components manage karne ke liye.

Ek cheez jispe mujhe garv hai: sidebar mein ek live connection indicator hai — backend reachable ho toh green, warna red with instructions. Saath hi yeh bhi dikhta hai ki pricing aur AI live chal rahe hain ya simulated. Outage simulate karne ke toggles bhi hain, taaki hum SRS ke required graceful fallbacks demo kar sakein.

40% milestone ke liye, chaaro screens backend ke saath end-to-end kaam kar rahe hain. Meri taraf se jo bacha hai woh hai visual polish aur input-validation messages, jo next sprint mein karenge."

🎤 Member 2 — Backend Developer (Flask + Business Logic)

Screen par khula rakho: backend.py, logic.py

"Maine backend banaya hai, jo SRS Section 7.3 ke according Flask use karta hai. Yeh system ka dimaag hai — yeh request routing, saara business logic, aur database aur external services ke calls handle karta hai.

Maine ek REST API banaya hai jo hamare SRS 3.11 ke sequence diagram se match karta hai. Main endpoints hain:

  • POST /generate-build — core flow,
  • POST /upgrade — upgrade advisor,
  • POST /builds aur GET /builds — build save aur list,
  • rating endpoints, aur authentication-gated admin endpoints jo token se protected hain (SRS Section 12).

Asli decision-making logic.py mein hoti hai. Main aapko build request ka flow batata hoon, kyunki yeh SRS Section 4 aur Section 9 ke business rules ko directly implement karta hai:

  1. Hum budget validate karte hain aur minimum se kam kuch bhi reject karte hain (SRS 9.1) — yeh hamara test case TC02 hai.
  2. Hum ek budget-aware algorithm se build generate karte hain jo saat parts mein paisa allocate karta hai, aur saath hi sasta essential parts ke liye paisa reserve rakhta hai taaki build hamesha complete ho.
  3. Hum compatibility checks chalate hain — CPU-motherboard socket, PSU wattage vs CPU+GPU power (safety margin ke saath), RAM type, aur case form factor (SRS 9.2, test case TC03). Agar kuch incompatible ho, toh ek repair loop compatible parts substitute karta hai, aur ek budget-trim pass guarantee karta hai ki hum kabhi budget cross na karein.
  4. Hum ek benchmark model se FPS estimate karte hain, aur usse "approximate" mark karte hain jaisa SRS chahta hai.
  5. Hum prices fetch karte hain aur ek AI explanation request karte hain.

Ek design principle jo maine follow kiya: backend stateless hai aur har request par database se live component catalogue padhta hai (SRS 5.6). Toh jab admin naya part add karta hai, woh turant recommendations mein aa jaata hai — restart ki zaroorat nahi.

40% par, poora build-generation aur upgrade flow kaam kar raha hai aur ₹42,000 se ₹2,50,000 tak ke budgets par test kiya gaya hai. Next sprint mein main FPS model aur error responses ko refine karunga."

🎤 Member 3 — Database Developer (SQLite + Integrations)

Screen par khula rakho: db.py (aur optional ai.py / pricing.py)

"Main data layer ka owner hoon. SRS Section 7.4 ke according hum development mein SQLite use karte hain, aur hamara schema aisa likha hai ki production ke liye MySQL par portable rahe.

Maine Section 8 ke ER diagram ka poora schema implement kiya hai — saat tables: User, Component, Build, BuildComponent, Game, Benchmark, aur Rating. Do associative tables important hain: BuildComponent build aur uske parts ke beech many-to-many relationship resolve karti hai, aur Benchmark build aur games ke beech many-to-many resolve karti hai, har pair ka estimated FPS store karke.

Ek design decision samjhata hoon: har component ke specs alag hote hain — CPU ka socket aur TDP hota hai, RAM ka type, PSU ki wattage. Dozens khaali columns banane ke bajaye, maine woh spec fields ek JSON blob mein specs column ke andar store kiye — yeh hamare data dictionary ke specs TEXT field se match karta hai aur schema ko clean aur MySQL-portable rakhta hai. Maine frequently filter hone waale fields jaise component type par index bhi lagaya (SRS 5.6). Database pehli baar chalne par khud create aur seed ho jaata hai, toh team clone karke turant chala sakti hai.

Maine hamare do external integrations bhi banaye (SRS 7.5), dono clean interfaces ke peeche isolated:

  • ai.py asli Gemini API ko call karta hai plain-language build explanation generate karne ke liye.
  • pricing.py live retailer price scraping karta hai requests aur BeautifulSoup se, plus ek cache jo repeated calls kam karta hai (SRS 5.1).

Dono optional hain aur gracefully fail hote hain — agar API key na ho ya network down ho, toh hum local explanation aur last-known prices with timestamp par fall back kar jaate hain. Yeh bilkul SRS Section 9.4 aur Section 10 ka reliability behavior hai.

40% par, database poora bana aur seed ho chuka hai, persistence kaam kar rahi hai — saved builds aur ratings restart ke baad bhi rehte hain — aur dono integrations fallbacks ke saath wired hain. Next sprint mein hum component aur benchmark data expand karenge."

💡 Delivery Tips
  • Scripts ke saath ek live demo zaroor dikhana — ₹90,000 budget par Cyberpunk ke liye build generate karo, phir sidebar toggle se fallback dikhao. Yeh ek interaction teeno layers ko saath kaam karte hue dikha deta hai.
  • Agar poocha jaaye "kya abhi baaki hai" — honest raho: visual polish, richer benchmark data, aur live scraping selectors real sites par tuning maangte hain (yeh hamari SRS §13 limitation hai).
